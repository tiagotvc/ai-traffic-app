RELATÓRIO TÉCNICO — AI TRAFFIC APP / ORION AGENCY
=================================================

Objetivo
--------
Este documento resume a arquitetura e os principais conceitos técnicos do projeto para estudo e apresentação em entrevistas de desenvolvimento.

RESUMO EXECUTIVO
----------------

O projeto é uma plataforma SaaS full-stack para gestão de tráfego pago. A aplicação centraliza contas, clientes, campanhas, públicos, criativos, métricas e automações, com integrações principais com Meta Ads e Google Ads.

A arquitetura é um monólito modular serverless:

Navegador
  -> Next.js App Router
     -> React Server/Client Components
     -> Middleware: autenticação + i18n
     -> Route Handlers REST (/api/*)
        -> Serviços de domínio (src/lib)
        -> TypeORM / Repositories
        -> PostgreSQL / Supabase
        -> Redis / Upstash
        -> APIs externas
           -> Meta Graph / Marketing / CAPI / WhatsApp
           -> Google Ads / OAuth / BigQuery / Maps
           -> Gemini / Anthropic / Cloudflare AI
           -> Stripe / Asaas
           -> Resend
           -> SearchAPI / IBGE / Nominatim

Não há um backend separado: frontend e backend vivem no mesmo projeto Next.js. Foram identificados aproximadamente 332 arquivos de endpoints, 100 páginas, 92 arquivos no diretório de entidades, 89 arquivos de migrations (incluindo o índice), 28 arquivos de testes e mais de 1.900 arquivos dentro de src.


1. LINGUAGENS UTILIZADAS
------------------------

O que é:
As linguagens são os meios usados para implementar a aplicação, suas configurações e sua infraestrutura.

Onde aparecem:
- TypeScript: praticamente todo o código em src, scripts e configurações.
- TSX/JSX: componentes e páginas React.
- JavaScript ESM: configurações e alguns scripts .mjs.
- SQL: migrations executadas pelo TypeORM.
- CSS: estilos globais, Tailwind e estilos de impressão.
- JSON: traduções, manifestos e configurações.
- PowerShell: scripts auxiliares para Windows.
- YAML: Docker Compose.

Por que são utilizadas:
TypeScript fornece tipagem para um domínio grande, com muitas respostas de API, DTOs e entidades. TSX permite construir a interface React. SQL/PostgreSQL oferecem persistência relacional e transações.

Como explicar em uma entrevista:
“O projeto é majoritariamente TypeScript, tanto no frontend quanto no backend. Isso permite compartilhar tipos e modelos mentais entre componentes, endpoints e serviços, reduzindo erros em integrações complexas.”


2. FRAMEWORKS
-------------

O que são:
Frameworks fornecem estrutura para roteamento, renderização, APIs, persistência e interface.

Onde aparecem:
- Next.js 16 com App Router.
- React e React DOM.
- Tailwind CSS.
- NextAuth/Auth.js v5 beta.
- next-intl para internacionalização.
- TypeORM.
- Inngest para tarefas assíncronas.
- Vitest para testes.

Por que são utilizados:
O Next.js reúne frontend, SSR e APIs em um único deploy. TypeORM abstrai PostgreSQL. NextAuth centraliza login e sessão. next-intl suporta português e inglês.

Como explicar em uma entrevista:
“É um full-stack Next.js com App Router. O framework entrega páginas, Server Components, middleware e endpoints REST. O domínio fica separado em serviços sob src/lib, enquanto TypeORM cuida da persistência.”


3. FRONTEND
-----------

O que é:
É a camada apresentada ao usuário e executada total ou parcialmente no navegador.

Onde aparece:
- src/app/[locale]: páginas e layouts roteados.
- src/components: componentes reutilizáveis.
- src/uxpilot-ui: telas e adapters do design importado.
- src/hooks: hooks de estado e carregamento.
- src/design-system: temas e elementos visuais.
- messages/pt-BR.json e messages/en.json: traduções.

Principais áreas: dashboard, clientes, campanhas, criador de campanhas, criativos, públicos, automações, relatórios, Agency Brain, Commander, Cortex, Labs, billing, configurações e administração.

Por que está organizado assim:
O App Router permite composição por layouts, agrupamentos de rotas e páginas localizadas. Os adapters de uxpilot-ui conectam os componentes visuais aos dados reais.

Como explicar em uma entrevista:
“A interface é React dentro do App Router. Há separação entre páginas, componentes, hooks e adapters. As telas consomem Route Handlers internos, enquanto os dados persistentes ficam no servidor.”


4. BACKEND
----------

O que é:
É a camada responsável por regras de negócio, autenticação, persistência e integrações externas.

Onde aparece:
- src/app/api: controllers HTTP do Next.js.
- src/lib: serviços e regras de domínio.
- src/db: entidades, repositories e migrations.
- src/auth.ts e src/auth.config.ts: autenticação.
- src/middleware.ts: proteção global e roteamento.
- src/lib/inngest: jobs assíncronos.

Por que é utilizado assim:
É um backend serverless integrado ao frontend, reduzindo a infraestrutura necessária. Isso exige atenção a timeout, conexões, idempotência e memória efêmera.

Como explicar em uma entrevista:
“O backend não é um serviço Express separado. Ele é composto por Route Handlers do Next.js. Os handlers funcionam como controllers e delegam a lógica para serviços e repositories TypeORM.”

6. BANCO DE DADOS
-----------------

O que é:
É o armazenamento persistente e relacional da aplicação.

Onde aparece:
O banco principal é PostgreSQL 16. Localmente pode rodar por Docker Compose. Em produção, o código recomenda uma URL de pooler do Supabase/PostgreSQL.

Os grupos de dados incluem usuários, tenants, membros, clientes, contas de anúncio, autenticações Meta/Google, métricas, billing, automações, criativos, relatórios, públicos, dados de IA, eventos e auditoria.

Por que é utilizado:
PostgreSQL combina integridade referencial, consultas analíticas, transações e tipos como jsonb e bytea.

Como explicar em uma entrevista:
“O PostgreSQL é a source of truth. O modelo é multi-tenant, e as consultas usam tenantId ou associações de clientes para evitar vazamento entre workspaces.”


7. ORM E MIGRATIONS
-------------------

O que é:
ORM mapeia classes TypeScript para tabelas. Migrations versionam mudanças no schema.

Onde aparece:
- TypeORM com decorators como @Entity e @Column.
- Classe base baseada em BaseEntity.
- Repositories centralizados.
- Migrations numeradas em src/db/migrations.
- synchronize: false.
- Reutilização da conexão em globalThis.

Por que é utilizado:
Evita SQL repetitivo e padroniza o acesso. Migrations tornam mudanças reproduzíveis e auditáveis.

Como explicar em uma entrevista:
“Usamos TypeORM com migrations explícitas. O synchronize fica desabilitado para proteger produção. Um advisory lock do PostgreSQL impede dois processos de executar migrations simultaneamente.”

Ponto de atenção: falhas em migrations de runtime são registradas, mas não derrubam imediatamente a aplicação, o que pode permitir incompatibilidade temporária entre código e schema.


8. AUTENTICAÇÃO E AUTORIZAÇÃO
-----------------------------

O que é:
Autenticação identifica o usuário; autorização decide o que ele pode acessar.

Onde aparece:
- src/auth.ts.
- src/auth.config.ts.
- src/middleware.ts.
- platform-auth.ts.
- app-context, workspace-members, entitlements e feature flags.

Métodos de login:
- email e senha;
- Google OAuth;
- Facebook/Meta OAuth.

A sessão usa JWT com duração de um dia. Existem papel de plataforma, membership de tenant, permissões por plano, acesso por cliente e feature flags.

Por que é utilizado:
A aplicação atende múltiplas agências e clientes, portanto precisa de isolamento por tenant e autorização por papel, plano e recurso.

Como explicar em uma entrevista:
“A autenticação é feita pelo Auth.js com sessão JWT e três provedores. A autorização ocorre em camadas: middleware, contexto do tenant, membership, papel administrativo e entitlements do plano.”

13. WEBHOOKS

14. JOBS, FILAS E CRONS
-----------------------

Vercel Cron agenda:
- billing worker: a cada hora;
- expiração de trial: a cada hora, no minuto 5;
- relatórios: a cada hora;
- automações: a cada hora, no minuto 15;
- BigQuery: a cada hora, no minuto 30;
- sync diário: 06:00 UTC;
- reconciliação de billing: 03:00 UTC;
- backfill: 04:00 UTC;
- cobrança PIX: 05:00 UTC.

Também existem SyncQueueJob, BillingJob, LookalikeJob, filas de backfill e workflows Inngest para Labs e Cortex.

Como explicar em uma entrevista:
“O sistema combina Vercel Cron para agendamento, filas no PostgreSQL para trabalho persistente e Inngest para workflows orientados a eventos.”


15. CACHE
---------

Onde aparece:
- Redis via REDIS_URL.
- Upstash Redis REST, preferido em Vercel.
- Fallback in-memory.
- Caches persistidos no PostgreSQL.
- sessionStorage para drill-down.
- localStorage para preferências.
- Cache de assets Meta, insights, criativos, pesquisas e recomendações.

Por que é utilizado:
Meta, SearchAPI e LLMs têm custo, latência e limites. O cache reduz chamadas repetidas.

Como explicar em uma entrevista:
“O cache é opcional e resiliente. Upstash ou Redis são usados quando configurados; caso contrário, alguns módulos degradam para memória ou banco.”


16. ARMAZENAMENTO DE ARQUIVOS
-----------------------------

Não foi encontrado um blob storage central.

- Imagens comunitárias ficam em PostgreSQL bytea.
- Logos podem ser data URI.
- Uploads grandes são divididos em chunks.
- Sessões e partes ficam no PostgreSQL.
- No commit, imagens e vídeos são enviados à Meta.
- PDFs são gerados sob demanda.

Como explicar em uma entrevista:
“Não existe S3 como camada principal. Uploads são temporariamente persistidos no Postgres, montados no commit e enviados à Meta. Em maior escala, eu migraria binários para object storage.”

24. ARQUITETURA GERAL
---------------------

Classificação:
- Monólito modular.
- Full-stack Next.js.
- Multi-tenant SaaS.
- Serverless-first.
- Orientada a integrações.
- Parcialmente event-driven.
- Com elementos de arquitetura em camadas.

Fluxo típico:

Página/Componente
  -> Hook/fetch
  -> Route Handler
  -> autenticação e tenant context
  -> serviço de domínio
  -> repository/TypeORM, cache e/ou API externa
  -> DTO JSON
  -> atualização da interface

Fluxo assíncrono:

Cron, webhook ou evento
  -> validação/idempotência
  -> job no PostgreSQL ou Inngest
  -> worker
  -> serviço
  -> API externa e persistência

Como explicar em uma entrevista:
“É um monólito modular porque existe um único deploy, mas o código é dividido por domínios. Isso reduz a complexidade operacional de microserviços sem concentrar toda a lógica em controllers.”

RESPOSTA CURTA PARA ENTREVISTA
-----------------------------

“Trabalhei em uma plataforma SaaS multi-tenant de gestão de mídia paga construída com Next.js, React e TypeScript. Ela usa o App Router tanto para frontend quanto para uma API REST serverless. A persistência é PostgreSQL com TypeORM e migrations explícitas. A autenticação usa Auth.js com email/senha, Google e Facebook, e a autorização combina tenant, membership, papel administrativo, feature flags e limites do plano.

A aplicação integra Meta Marketing API, CAPI, WhatsApp, Google Ads, BigQuery, Gemini, Claude, Stripe, Asaas e Resend. Operações demoradas ou recorrentes usam filas persistidas, Inngest e Vercel Cron. Redis/Upstash é usado como cache opcional, com fallback. A arquitetura é um monólito modular: existe um único deploy, mas os domínios de campanha, billing, automação, relatórios e IA são separados em serviços.”
